01

Why PureScript eliminates entire bug classes

React's mental model is fundamentally broken for correctness. useState creates mutable references that close over stale values. useEffect dependencies are stringly-typed and unverifiable. Context triggers cascading re-renders through referential inequality.

PureScript's Halogen uses an entirely different architecture: explicit state machines with algebraic data types for actions. There's no 'dependency array' because there are no implicit dependencies. State transitions are pure functions. Side effects are tracked in the type system via the Aff monad.

-- React: runtime bug
useEffect(() => {
  fetchData(userId) // stale closure if userId changes
}, []) // oops, forgot dependency

-- PureScript: compile-time error
handleAction :: Action -> H.HalogenM State Action ...
handleAction (Fetch userId) = do
  result <- H.liftAff $ fetchData userId  -- userId is explicit
  H.modify_ _ { data = result }           -- state update is pure

The type system doesn't let you forget. There's no escape hatch. No 'any'. No '@ts-ignore'. If it compiles, the state machine is coherent.

02

Formal verification with Lean4

Our Radix Pure Compiler doesn't just generate code—it generates proven-correct code. We write specifications in Lean4, a dependently-typed proof assistant, and extract PureScript that satisfies those specifications by construction.

For ARIA semantics, this means: if a component is a listbox, the generated code will have role="listbox". Not because we tested it. Because the type system encodes the ARIA specification and the compiler rejects non-compliant code.

-- Lean4: ARIA role specification
inductive AriaRole where
  | dialog | listbox | menu | tooltip

def ariaRole (component : ComponentType) : AriaRole :=
  match component with
  | .select => .listbox    -- theorem: Select → listbox
  | .dialog => .dialog     -- theorem: Dialog → dialog  
  | .menu => .menu         -- ...proven at compile time

-- Generated PureScript has correct roles by construction
-- No runtime check. No test. Mathematical certainty.

This isn't academic masturbation. WCAG 2.1 AA compliance becomes a type-checking problem. Your accessibility audit becomes a formality because correctness is baked into the compiler.

03

Halogen's state machine model

Every Halogen component is an explicit state machine with four parts:

  • State — an algebraic data type describing all possible states
  • Action — an ADT enumerating all possible events
  • handleAction — a pure function: (State, Action) → State + Effects
  • render — a pure function: State → HTML

No hooks. No implicit re-renders. No stale closures. The component is a pure function from state to UI, with explicit effect handling. React's 'rules of hooks' don't exist because the architecture doesn't need them.

type State = { count :: Int, loading :: Boolean }

data Action = Increment | Decrement | StartLoad | FinishLoad Int

handleAction = case _ of
  Increment -> H.modify_ _ { count = _ + 1 }
  Decrement -> H.modify_ _ { count = _ - 1 }
  StartLoad -> do
    H.modify_ _ { loading = true }
    result <- H.liftAff fetchCount
    handleAction (FinishLoad result)
  FinishLoad n -> H.modify_ _ { count = n, loading = false }
04

Property testing > unit testing

Unit tests check specific examples. Property tests generate thousands of random inputs and verify invariants hold for all of them. The test framework finds edge cases you'd never think of.

For a shopping cart, instead of testing 'add item, check total', you test properties like:

  • ∀ items: total ≥ 0
  • ∀ items: add(item) then remove(item) = identity
  • ∀ items: order of additions doesn't affect total

QuickCheck generates thousands of random carts and verifies these properties. When it finds a counterexample, it shrinks it to the minimal failing case. One property test replaces dozens of unit tests and catches bugs unit tests miss.
